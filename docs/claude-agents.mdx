# Claude Agents

This repo defines a set of specialized agent personas under `.claude/agents/`, referenced from
`.claude/.claudecode.json` and `.claude/prompts/bootstrap-library.md`. They aren't separate running
processes — they're **role definitions** Claude Code is expected to read and follow when working in
this repo, each scoped to one concern so a single change gets checked from every relevant angle
instead of relying on one generalist pass.

## Standard workflow order

Per `workflow-orchestrator-agent.md`, a full feature/component task runs through agents in this
order — each phase validates the previous one rather than re-doing it:

```txt
1. planner-agent            → component contract, stories plan, testing requirements
2. architect-agent           → architecture/composition/folder-structure approval
3. a11y-agent                → accessibility requirements
4. performance-agent         → rendering/bundle recommendations
5. task-runner-agent         → implementation + tests + stories
6. testing-strategy-agent    → testing/coverage approval
7. documentation-agent       → docs/examples/Storybook clarity approval
```

Shortcut workflows exist for urgent cases and skip straight to the relevant agents:

- **Emergency** (urgent bug fix): `architect-agent` → `a11y-agent` → `task-runner-agent`
- **Refactor**: `architect-agent` → `performance-agent` → `task-runner-agent` → `testing-strategy-agent`
- **Accessibility incident**: `a11y-agent` → `task-runner-agent` → `testing-strategy-agent`

## When rules conflict: the policy engine

`policy-engine.md` defines a strict priority order so agents don't produce contradictory guidance —
from highest to lowest:

1. **P0 — Safety & Accessibility** (`a11y-agent`) — overrides everything; a violation stops execution.
2. **P1 — Repository Governance** (`repository-governance-agent`)
3. _(lower tiers continue in the source file for architecture, performance, and style concerns)_

## Rules that shaped decisions in this repo

A few concrete rules from these agent definitions that are visible elsewhere in this codebase, so you
know where they came from:

- _"All imports MUST use configured aliases... Relative imports are forbidden outside of same folder"_
  (`workflow-orchestrator-agent.md`) → [Import Aliases](/docs/documentation-import-aliases--docs).
- _"No component is considered complete unless: test file exists... accessibility scenarios are
  covered where applicable"_ → [Testing And Coverage](/docs/documentation-testing-and-coverage--docs),
  `.claude/.claudecode.json`'s `testing.minimumCoverage: 90`.
- _"All architectural decisions MUST go in /docs/adr"_ → see `docs/adr/` for the ADRs already on file
  (library architecture, Tailwind strategy, build/distribution strategy).

## Where this is actually enforced

There's no code that mechanically runs these agents — they're instructions for whoever (human or
Claude Code) is doing the work to follow. Treat `.claude/agents/*.md` as the source of truth for "how
we work here" the same way you'd treat a CONTRIBUTING.md, just organized by concern instead of as one
long document.
