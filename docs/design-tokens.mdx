# Design Tokens

All visual values (colors, spacing, radius, typography) live in `@inzumer/tokens`, in three layers
that build on each other. Components never see layer 1 or 2 directly — they only ever consume layer 3
(CSS custom properties).

## 1. Base tokens (`packages/tokens/src/tokens/base/`)

Plain TypeScript objects — the raw scale, with no semantic meaning attached yet:

- **`colors.ts`** — `BaseColors`: `primary`, `neutral`, `danger`, `success`, `warning`, `info`, each a
  scale of steps (`50`...`950`, not every color defines every step).
- **`spacing.ts`**, **`radius.ts`**, **`typography.ts`** — scales for spacing, border-radius, and
  font family/size/weight/line-height/letter-spacing.

## 2. Semantic tokens (`packages/tokens/src/tokens/semantic/`)

Map base colors to **roles** — `lightSemanticTokens` and `darkSemanticTokens`, both shaped as
`SemanticTokens`: `surface`, `text`, `border`, `button` (per variant: `primary`/`secondary`/`ghost`/
`destructive`), `input`. This is the layer that changes between light and dark mode — the roles stay
the same, the underlying color reference changes.

## 3. CSS custom properties (`packages/tokens/src/css/variables.css`)

The base and semantic tokens above are hand-mirrored into plain CSS custom properties — this is the
**only** layer components actually read from from (`Button.tsx` uses
`bg-[var(--btn-primary-bg)]`, never a token object import):

```css
:root {
  --color-primary-500: 59 130 246; /* raw RGB channels, no rgb() wrapper */
  --surface-primary: rgb(var(--color-neutral-50));
  --btn-primary-bg: rgb(var(--color-primary-600));
  --btn-primary-bg-hover: rgb(var(--color-primary-700));
  /* ...surface/text/border/btn-*/input-* for every role */
}

[data-color-scheme='dark'] {
  --surface-primary: rgb(var(--color-neutral-950));
  --btn-primary-bg: rgb(var(--color-primary-500));
  /* ...dark-mode values for the same variable names */
}
```

Colors are stored as **raw RGB channels** (`59 130 246`, not `rgb(59, 130, 246)`) specifically so
Tailwind's `<alpha-value>` placeholder works for opacity utilities like `bg-primary-500/50`.

Why a hand-maintained CSS file instead of generating it from the TS tokens at build time? Simplicity —
there are few enough tokens that keeping both in sync by hand is low-effort, and it avoids a codegen
step in the build. If the token set grows significantly, generating `variables.css` from
`baseTokens`/`lightSemanticTokens`/`darkSemanticTokens` would be a reasonable follow-up (see
`packages/tokens/src/utils/inject-css-vars.ts`'s `buildCssVars`/`buildSemanticCssVars`, which already
do this flattening — just for runtime injection rather than the static file).

## The Tailwind preset (`packages/tokens/src/tailwind/preset.ts`)

`DefaultPreset` (exported from `@inzumer/tokens/tailwind`) generates Tailwind color/font/spacing/
radius utilities that resolve to the CSS variables above — e.g. `bg-primary-500` compiles to
`background-color: rgb(var(--color-primary-500) / <alpha-value>)`, not a literal color. It also sets
`darkMode: ['selector', '[data-color-scheme="dark"]']` so `dark:` variants and the CSS above use the
same attribute.

Consumers add it to their own Tailwind config:

```ts
import type { Config } from 'tailwindcss';
import { DefaultPreset } from '@inzumer/tokens/tailwind';

export default {
  presets: [DefaultPreset],
  content: ['./src/**/*.{ts,tsx}'],
} satisfies Config;
```
